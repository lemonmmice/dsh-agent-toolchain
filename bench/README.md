# Benchmark (pilot)

A harness for measuring an external agent CLI on real coding tasks, in two modes:

| mode | agent toolset |
|---|---|
| `baseline` | the CLI's built-in tools only (read / edit / shell) |
| `toolchain` | built-in tools **plus** the dsh-agent-toolchain MCP server (`mcp/server.mjs`): build loop, capture store, memory, failure corpus, `verify_report` |

The headline metric is **cost per verified task**: a task counts as *verified* when
the agent's patch, applied to a clean checkout together with a hidden verification
patch, makes the task's verify command exit 0.

## What is a task

A task is a real, merged bugfix in a public open-source repository, packaged
SWE-bench style:

```
bench/tasks/<id>/
  config.json     repo URL, base commit, gold commit, verify command, budgets
  prompt.md       the written bug report the agent sees
  verify.patch    the test-only part of the real fix commit (HIDDEN from the agent)
  gold.patch      the real fix, for reference (HIDDEN from the agent)
```

`verify.patch` and `gold.patch` are generated by splitting the real fix commit:
`git diff <base> <gold> -- <test paths>` and `-- <source paths>`. Before a task
is used, its baseline is validated twice: `base + verify.patch` must fail the
verify command, and `base + verify.patch + gold.patch` must pass it.

## Privacy and answer secrecy

Task packages live in `bench/tasks/` and are **not committed** to this public
repository (see `.gitignore`). Two reasons:

1. **Answer secrecy** — publishing the task would publish its answer, which
   poisons the benchmark for future runs.
2. **No environmental signal** — the set of tasks an author benchmarks against
   can hint at their professional environment. The public repo ships the
   harness, the methodology and anonymized aggregated numbers only; task
   identity stays local.

`scripts/check.mjs` hard-fails if anything under `bench/tasks/`, `bench-runs/`
or `bench/local.env` is ever tracked by git.

Anti-gaming measures in the harness: the agent's checkout has its git remotes
removed, the hidden verification patch never touches the agent's workspace, and
every run records whether the agent's patch touched the hidden test paths.

## Running a run

Requirements: Node 20+, the agent CLI on PATH, and the .NET SDK pinned by the
task (`BENCH_DOTNET_DIR` may point at a locally installed SDK).

```powershell
# one baseline run
npm run bench -- --task <task-id> --mode baseline

# one toolchain run
npm run bench -- --task <task-id> --mode toolchain

# repeat a mode for variance
npm run bench -- --task <task-id> --mode baseline --runs 2

# pin the model, cap turns, use a local clone mirror, agent-env overrides
npm run bench -- --task <task-id> --mode toolchain --model <name> --max-turns 40 `
  --reference <path-to-local-mirror> --local-env bench/local.env
```

Each run writes `bench-runs/<run-id>/` (agent log, `agent.patch`, verify log,
`run.json`) and appends one line to `bench-runs/results.jsonl`. Aggregated,
anonymized results are published in `bench/pilot/`.

## Metrics per run

- `turns`, `durationMs` — from the CLI's result JSON
- `usageInputTokens` / `usageOutputTokens` / cache tokens
- `costUsd` — as reported by the CLI for the configured model
- `verified` (bool), `verifyExitCode`, `verifyReason`
- `patchedTests` (bool) — did the agent touch the hidden test paths
- `mcpToolsVisible` (bool, toolchain only) — a 1-turn machine probe ran after
  the agent and confirmed the MCP tools were listed among the agent's tools;
  a toolchain run with `mcpToolsVisible: false` is marked `modeValid: false`
  and must be excluded from comparisons (guards against CLI flags silently
  dropping MCP servers — which `--bare` does, empirically)
- `patchFiles` — files the agent changed

Cost per verified task = sum of `costUsd` over verified runs of a mode ÷ number
of verified runs of that mode.

## Known limitations (pilot)

- Single machine, one task, few runs: this is a pipeline pilot, not a
  publication-grade benchmark. No statistical claims are made.
- The agent CLI's default model is used unless `--model` pins one; both modes
  must use the same model for a fair comparison.
- Web access is blocked at the tool level (`--allowedTools` excludes
  WebSearch/WebFetch), on top of the prompt's instruction and removing git
  remotes; MCP tools remain available in toolchain mode.
- The toolchain MCP server is exposed as-is, including tools that are
  irrelevant to the task at hand; discovering which tools help is part of the
  measured behavior.
- Costs are as reported by the agent CLI; they do not include the MCP server
  itself (local, free).
